References for observing outbound traffic

Understand the values of metric labels and other configuration, and get examples of queries. An egress Gateway object emits the same metrics, access logs, and traces as a Gateway object that handles incoming traffic.

Important

To use an egress Gateway object, you must use OpenShift Service Mesh as the Gateway API provider. The OpenShift Container Platform Cluster Ingress Operator (CIO) is not supported for outbound-traffic use cases.

Prometheus queries for egress traffic

Use the following Prometheus queries to analyze outbound traffic after your monitoring stack scrapes the egress Gateway object. Each query filters on the workload name of the egress gateway proxy to exclude traffic that enters the cluster.

Queries on gateway metrics

In the following queries, replace <kuadrant_egressgateway>-istio with the workload name of your egress gateway proxy.

  • Request rate for each external destination:

    sum(rate(istio_requests_total{source_workload="<kuadrant_egressgateway>-istio"}[5m])) by (destination_service)

  • Proportion of requests that return a client or server error:

    sum(rate(istio_requests_total{source_workload="<kuadrant_egressgateway>-istio",response_code=~"[45].."}[5m]))
/
sum(rate(istio_requests_total{source_workload="<kuadrant_egressgateway>-istio"}[5m]))

    This query counts errors at the HTTP level. Connection failures and timeouts to the external service usually produce a 503 or 504 status code, so the query includes them. Requests for which the gateway sent no HTTP response, such as a disconnect by the calling workload, carry the value 0 in the response_code label and are excluded.

  • Requests for which the gateway sent no HTTP response:

    sum(rate(istio_requests_total{source_workload="<kuadrant_egressgateway>-istio",response_code="0"}[5m]))

  • 99th percentile latency for each external destination:

    histogram_quantile(0.99,
    sum(rate(istio_request_duration_milliseconds_bucket{source_workload="<kuadrant_egressgateway>-istio"}[5m])) by (destination_service, le)
)

  • Response bytes transferred for each external destination:

    sum(rate(istio_response_bytes_sum{source_workload="<kuadrant_egressgateway>-istio"}[5m])) by (destination_service)

  • Requests that match no route, which indicates a misconfigured client:

    sum(rate(istio_requests_total{source_workload="<kuadrant_egressgateway>-istio",response_flags="NR"}[5m])) by (destination_service)
Queries on custom labels

The following queries require a TelemetryPolicy custom resource (CR) that adds the workload and destination labels to the Connectivity Link data plane metrics.

  • Request rate for each calling workload:

    sum(rate(authorized_calls[5m])) by (workload)

  • Rate limited requests for each workload and destination:

    sum(rate(limited_calls[5m])) by (workload, destination)

  • Token consumption for each workload, for a route that carries a TokenRateLimitPolicy CR:

    sum(rate(authorized_hits[5m])) by (workload)

  • External services that each workload calls:

    sum(rate(authorized_calls[5m])) by (workload, destination)

Label expressions for egress metrics

The Connectivity Link data plane attaches each label of a TelemetryPolicy custom resource (CR) to both the rate limit check descriptor and the report descriptor.

The check runs in the request phase, before the external service responds, so every Common Expression Language (CEL) expression must resolve at that point.

The request.scheme attribute describes the connection from the workload to the gateway, not the connection from the gateway to the external service. A workload that calls the gateway over plain HTTP reports http even when the gateway originates TLS to the external service. To break metrics down by response status, use the response_code label on the istio_requests_total metric instead.

Label cardinality

Every distinct combination of label values creates a time series, so a high-cardinality expression on a busy egress Gateway object consumes a large amount of storage in your monitoring stack.

The source.address attribute is the most common cause of high cardinality, because it includes the ephemeral source port and therefore produces a new series for every connection. Envoy renders the address as 192.0.2.24:54146 for IPv4 and [2001:0DB8:85a3::8a2e:370:7334]:41235 for IPv6.

To record only the address, remove everything after the last colon as shown in the following snippet:

source_ip: source.address.substring(0, source.address.lastIndexOf(":")).replace("[", "").replace("]", "")

The lastIndexOf function finds the colon that precedes the port, which leaves the colons inside an IPv6 address unchanged, and the two replace functions remove the brackets. Do not use source.address.split(":")[0], which works for IPv4 but truncates an IPv6 address to [2001.

Prefer labels with a bounded set of values, such as the workload identity, the destination host, or the request method. Avoid request.path unless the set of paths is small and known, because an API with a path for each resource produces an unbounded number of series.

Effect of an expression that cannot resolve

An expression that references an unavailable attribute is not dropped. Evaluating the Limitador descriptor fails, the Gateway object logs the following message for every request, and metrics are not recorded for the affected route:

Example log entry
Failed to evaluate message builder: CelError::Resolve { UndeclaredReference("response") }

Whether the request itself succeeds depends on the failure mode of the services on the route. The rate-limit services default to a failure mode of allow. A route that carries only a RateLimitPolicy CR continues to return a 200 status code but loses its metrics. A route that also carries an AuthPolicy CR, which defaults to a failure mode of deny, can instead fail with a 500 status code. A route with no rate limit policy does not build a descriptor and is unaffected.

The policy continues to report that it is accepted and enforced, so check both the traffic and the metrics after you apply a new label.

Response flags

Response flags show where and why a request failed. The following flags are the most relevant to outbound traffic:

Table 42. Response flags on egress traffic
Flag Meaning Interpretation on egress

-

No flags

The request completed, either successfully or with an error from the external service

NR

No route found

No HTTPRoute object matches the destination hostname

UH

No healthy upstream

DNS resolution succeeded, but a healthy endpoint is not available

UF

Upstream connection failure

The Gateway object could not connect to the external service

UT

Upstream request timeout

The external service did not respond within the configured timeout

DC

Downstream connection termination

The calling workload disconnected before the response arrived

URX

Upstream retry limit exceeded

Every retry to the external service failed

UPE

Upstream protocol error

The protocol of the external service does not match the expected protocol

The distinction between - and the other flags is important. A 503 status code with the - flag means that the external service returned the error. A 503 status code with the UF flag means that the Gateway object never reached the external service.

Access log patterns for common egress failures

The following access log entries show the patterns that the most common outbound request failures produce, and the conclusion that you can draw from each one.

Error from the external service
Example access log entry
[...] "GET /get HTTP/1.1" 503 - via_upstream - "-" 0 162 326 326
  "192.0.2.18" "curl/8.21.0" "e0d56588-1f9c-4d72-9a1e-6b4a39f0c2d1" "api.example.com"
  "198.51.100.35:443" outbound|443||api.example.com ...

A 503 status code with the - response flag and the via_upstream response code details means that the external service returned the error, not the gateway. The upstream host field shows the address that served the response. This field is useful when the external service has several back ends.

No route for the destination
Example access log entry
[...] "GET /get HTTP/1.1" 404 NR route_not_found - "-" 0 0 0 -
  "192.0.2.18" "curl/8.21.0" "a326cb9d-52e7-4c31-bb90-8e41d27a5f60" "unknown-api.example.com"
  "-" - - 192.0.2.17:80 192.0.2.18:41290 - -

The NR response flag and the route_not_found response code details mean that no HTTPRoute object matched the hostname in the authority field, and that the gateway selected no upstream. Verify that an HTTPRoute object exists for the destination, and that the external hostname has a ServiceEntry object if it needs one to be routable.

Latency in the gateway compared with the external service

Two timing fields show where the time was spent. The duration field holds the total time from the moment the Gateway object received the request to the moment it returned the response to the workload. The upstream service time field holds the time that the external service took to respond.

Example access log entry
[...] "GET /get HTTP/1.1" 200 - via_upstream - "-" 0 1172 1879 1650 ...

In this entry, the total duration is 1,879 milliseconds and the upstream service time is 1,650 milliseconds, so about 229 milliseconds were spent outside the external service.

That time covers TLS origination, policy evaluation, proxy processing, and network transit. A gap that is large and persistent indicates a problem on the Gateway object side. For example, latency in policy evaluation, an exhausted connection pool, or a network fault. When the two values are close, most of the request time goes to waiting for the external service.

Timeout in the calling workload

A 0 status code with the DC response flag means that the calling workload closed the connection before the external service responded. Verify whether the external service is slow, or whether the timeout of the calling workload is too short.

Span hierarchy for an outbound request

A request that passes through an egress Gateway object that carries an AuthPolicy custom resource (CR) and a RateLimitPolicy CR produces the following spans.

Example span hierarchy of the Connectivity Link filter trace
[kuadrant-filter] kuadrant_filter
├─ [kuadrant-filter] grpc (action=ratelimit)
│  ├─ [kuadrant-filter] grpc_request (ShouldRateLimit)
│  │  └─ [limitador] should_rate_limit
│  │     └─ [limitador] check_and_update
│  └─ [kuadrant-filter] grpc_response
├─ [kuadrant-filter] grpc (action=auth)
│  ├─ [kuadrant-filter] grpc_request (Check)
│  │  └─ [authorino] envoy.service.auth.v3.Authorization/Check
│  │     └─ [authorino] Check
│  └─ [kuadrant-filter] grpc_response
└─ [kuadrant-filter] headers (HttpResponseHeaders)

The wasm-shim module creates a root span and a child span for each policy evaluation, and propagates the trace context to the Authorino and Limitador components through gRPC metadata.

The Gateway object trace of the same request holds the proxy spans for the route to the external service.
